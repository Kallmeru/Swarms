# SWARMS: frontend

No build step, no bundler, no framework. Two pages:

- `index.html` — the dashboard: pitch, live benchmark numbers, team. Entry point.
- `os.html` — the demo itself, a desktop simulation with the animated pipeline.

## Two modes, one codebase

The page probes `/api/health` on load and picks:

- **LIVE** — a backend answered, so every run is executed on demand by the
  real pipeline. The `live_console` window lets a visitor paste any document
  and watch the policy engine decide about text nobody wrote a fixture for.
- **REPLAY** — nothing answered (the static GitHub Pages build), so it
  animates the traces `benchmark/run_benchmark.py` recorded into `web/data/`.

The event format is identical either way, which is the only reason one set of
rendering code serves both. The badge in the menu bar says which mode is
active.

```bash
python -m server                      # LIVE  -> http://localhost:8000
python -m http.server 8000 -d web     # REPLAY -> http://localhost:8000
```

## Data contract

Everything in `web/data/` is generated by `python -m benchmark.run_benchmark`:

- `manifest.json` — fixture list, including the payload text each one feeds the reader
- `benchmark_summary.json` — aggregates: containment rate, utility retained, false positives
- `<attack_id>_off.json` / `<attack_id>_on.json` — ordered event arrays, one pair per fixture

These are real output from running the pipeline, not hand-written samples,
and the Pages workflow regenerates them on every deploy so the site never
animates a stale commit. The event schema is documented in full in
`docs/swarms-integration-schema.md`.

## Third-party

`vis-network` (graph) and `Chart.js` (bar chart) from CDN, both only on
`os.html`. Everything else, the dot field, decrypt text, target cursor,
option wheel and the synthesized UI sounds, is local: `effects.js` and
`sound.js`, no audio files.

Nothing in `web/` executes anything or holds any state. In LIVE mode it makes
two API calls; in REPLAY mode it reads JSON. That is the whole surface.
